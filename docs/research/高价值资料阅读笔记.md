## 2. 微软的发现协议：最接近我们需要的提问底座

### 来源实际提供什么

微软工程团队的项目发现文档围绕可测量的业务问题、是否需要机器学习、谁使用结果、如何判断成功、领域专家与数据条件组织讨论，并要求形成共享的问题定义。它同时提醒效果评估需要考虑原有做法和其他变化，而不能只看一个改善后的数字。见 [D12 原文](https://microsoft.github.io/code-with-engineering-playbook/ml-and-ai-projects/envisioning-and-problem-formulation/)。

这比“行业、人数、营收、预算、拍板人”的售前表更适合作为本产品的起点。后者可以帮助卖服务，却不足以说明用户是否真的需要服务。

### 本项目可以转成的追问链

| 用户回答 | 下一问 | 区分什么 | 收口时记录什么 |
|---|---|---|---|
| “想让销售更智能” | “最近哪次销售决策，因为缺信息或处理太慢出了问题？” | 具体业务需求与笼统愿望 | 事件、角色、决策和影响 |
| “让 AI 推荐客户” | “现在优秀销售怎么选？给他同样资料，他能做出稳定判断吗？” | 存在可描述规律，还是专家也缺信息 | 当前人工能力与数据缺口 |
| “提高成交率” | “哪个客户群、哪段时间、由谁统计？同时会改变价格或活动吗？” | 指标定义与混杂因素 | 分母、窗口、对照和同期变化 |
| “做个更聪明的模型” | “如果现有 CRM 的规则筛选能解决大部分问题，哪里仍然过不去？” | 是否真的需要定制 AI | 已有替代与剩余缺口 |
| “老板会用” | “实际每天根据这个结果做事的人是谁？他目前怎么绕过这个问题？” | 出资者与使用者不同 | 用户、工作流和现有补救 |
| “先上线再说” | “上线后谁维护数据和判断标准？什么情况会暂停使用？” | 能运行与能持续使用不同 | owner、维护、停止条件 |

专业性体现在对回答的处理。例如领域专家拿现有资料也无法判断时，Agent 应暂时转向信息补齐，而不是把所有问题都解释成缺大模型。

### 与用户确认的最小文本

> 我理解我们要改善的是【某角色在某情境下的某项决策】，当前主要影响是【有口径的影响】。现有做法是【基线】，成功需要【可观察变化】，必须保留【约束】。目前仍不能确认【未知】。这是否准确？有没有我理解错或漏掉的地方？

该模板是本项目设计。确认用于防止误解，不代表目标、数据或因果关系因此已经验证。

## 3. Palantir：把“企业数字孪生”收缩到一个决策闭环

### 来源实际提供什么

Palantir 的官方说明以 **Data、Logic、Action、Security** 组织业务决策：信息、业务逻辑、执行行动和安全边界共同支持组织运行。Action types 文档进一步描述对象变化、业务逻辑与验证。它们是产品架构文档，不是关于“企业多少人就该请 FDE”的标准。见 [Why create an Ontology?](https://www.palantir.com/docs/foundry/ontology/why-ontology/)、[Action types overview](https://www.palantir.com/docs/foundry/action-types/overview/)。

### 本项目的四类问题

| 维度 | 面向业务用户的问法 | 需要查证的材料 | 判断改变的信号 |
|---|---|---|---|
| Data | “拿上次订单为例，做决定时看了哪些信息？哪项直到最后也没法确认？” | 同一事件在不同系统的记录、更新时点、口径 | 有接口但语义冲突，或数据本来足够 |
| Logic | “最后为什么选择这个办法？正常规则与例外由谁解释？” | 操作规则、例外记录、人工判断依据 | 规则清楚可用标准软件，或存在现场特异判断 |
| Action | “决定后谁在哪个系统改了什么？还有哪些人要手工接着做？” | 下游动作与交接、回写、失败补救 | 仅生成文本，或涉及多系统执行 |
| Security | “谁有权批准？做错能否撤回？谁能发现和接管？” | 授权、审批、审计与责任信息 | 低影响可复核，或高影响需要专业控制 |

四类问题应围绕同一个真实事件穿起来。把它们变成全企业架构调查，会让初次访谈过重，也容易诱导用户购买庞大平台。

**最小业务地图**可以是“一次订单异常 → 两处信息 → 一个规则判断 → 一次批准 → 一个结果记录”。能够共享、复查并改善这个闭环，才有资格讨论进一步扩展；不必先承诺完整企业数字孪生。

## 4. FDE 从业者经验：我们确认了什么

### 4.1 First Round 的原始访谈与回忆中的面试题

这篇原始采访讨论了不同公司怎样设置 FDE 职责、如何识别业务与技术兼具的人，以及何时一般实施支持可能已经足够。其中 Shilpa Balaji 回忆了 Palantir 招聘中的情境：向候选人解释内幕交易，再观察他会要什么数据、向客户问什么、分析时看什么。这是受访者的岗位经历回忆，不能标为当下官方面试题库。见 [P23 原文](https://review.firstround.com/so-you-want-to-hire-a-forward-deployed-engineer/)。

这个例子的价值是**在业务尚未说清时，检查人会怎样建立问题与证据**。本产品可设计类似模拟，但应让客户根据提问逐步提供条件，而不是把完整答案一次塞给模型。

项目模拟示例：

```text
用户：物流一直出问题，老板要一个 AI 指挥台。
第一个分歧：问题是看不见状态，还是看见后不知道怎么办？
第二个分歧：若不知道怎么办，是规则冲突、责任冲突，还是信息不够？
第三个分歧：目前谁处理例外，为什么现有软件覆盖不了？
第四个分歧：是否有内部团队、标准工具或流程改变可以解决？
输出：暂定服务路径、改变判断的条件与最小补证动作。
```

**重要边界**：原文主要回答“技术供应商是否要建 FDE 团队”。我们的产品回答“客户企业是否应购买 FDE 服务”。二者相关，但不能把供应商招人的收入结构、目标客户规模或配置比例，直接变成客户分诊阈值。

### 4.2 Baseten 的三篇原始材料

| 来源 | 有价值的经验 | 本产品可用的提问 | 不该怎么用 |
|---|---|---|---|
| [Vlad Shulman：FDE on the frontier of AI](https://www.baseten.co/blog/forward-deployed-engineering/)（P17） | 探索客户问题、工程交付与产品反馈相连；职责随产品和不确定性变化 | “哪里需要现场发现，哪里只是既有功能实施？这项工作是否值得定制？” | 不能把公司内部产品回流目标视为行业定律或用户转介标准 |
| [Het Trivedi：What I learned as an FDE](https://www.baseten.co/blog/what-i-learned-as-a-forward-deployed-engineer-working-at-an-ai-startup/)（P18） | 与客户一起面对性能、成本、生产条件和交接的真实限制 | “最近一次真实业务高峰发生什么？成功还需要满足哪些运行条件？” | 个人时间分配不是所有 FDE 的标准；其模型工程任务不代表本项目要训练模型 |
| [Joey Zwicker 访谈](https://www.baseten.co/blog/joey-zwicker-joins-baseten-as-head-of-fde/)（P19） | 共同设计、讲清取舍、可信的时间与异常沟通、经验复用 | “你最担心哪种失败？有什么必须保留的约束？出了问题谁接管？” | 受访者理念和个案不是已验证的企业成熟度量表 |

从这些材料抽卡，应优先记录作者面对的**冲突和约束**。如业务价值与上线速度、客户特异性与产品复用、演示效果与生产条件。不要只存“FDE 应该懂技术、懂业务、会沟通”。

## 5. 官方咨询案例：值得借鉴完整推导，不值得复制答案

### 5.1 Bain Coffee Shop Co.：先问值不值得

官方练习从是否开店的投入决策出发，逐步澄清范围、市场机会、成本与达到收支条件所需的需求，再给出带条件的建议。正文可以阅读，但部分图表是图片，本次不引入其具体数字。见 [D16 完整练习](https://www.bain.com/careers/hiring-process/interviewing/coffee-case-study/)。

迁移到本项目的重点：

1. **目标**：“你希望这笔投入换来什么，是可兑现收入、降低费用，还是降低风险？”
2. **范围**：“先覆盖哪个业务、哪类事件？暂时不覆盖什么？”
3. **可兑现性**：“省下的时间会用在哪里？确实有更多业务可做吗？”
4. **成本完整性**：“除了顾问费，还需要哪些内部人员、集成、维护和培训？”
5. **条件建议**：“目前哪些条件支持小范围发现，哪些未确认，哪种情况应停止？”

Agent 应能回答“现在不用花这笔钱”。如果总是推出 R4，再补一个 ROI 故事，就偏离了本产品的分诊定位。

### 5.2 Bain FashionCo.：先找解释，再比行动

官方案例先分析业绩变化与客户趋势，然后比较路径的实际可行性、简化经济测算和长期风险。它说明建议不应只有一个算式或选项名。模拟材料中的假设不能成为真实行业数据。见 [D17 完整练习](https://www.bain.com/careers/hiring-process/interviewing/fashion-case-study/)。

企业 AI 访谈可以采用以下顺序：

```text
现象：交付变慢。
解释：订单复杂度变化？数据延迟？资源冲突？例外规则？操作能力？
区分问题：最近一单，等待主要发生在哪里？同期改变了什么？
路径：现有软件配置／流程调整／内部改造／FDE 发现。
比较：能否覆盖问题、内部代价、主要风险、可撤回程度。
建议：先验证哪条解释；什么新信息会改变所选路径。
```

该迁移是本项目设计，不是 Bain 发布的 FDE 访谈协议。真实客户信息不齐，要允许“先看样例、再决定”，不能模仿练习中的整齐资料做确定性结论。

## 6. 详细面试准备材料：有价值，但来源性质要讲清楚

本轮读到一组公开 FDE 准备材料：[轮次说明](https://github.com/aishwaryanr/awesome-generative-ai-guide/blob/main/interview_prep/roles/forward-deployed-engineer/rounds.md)（P20）、[问题与解答](https://github.com/aishwaryanr/awesome-generative-ai-guide/blob/main/interview_prep/roles/forward-deployed-engineer/questions.md)（P21）、[资源目录](https://github.com/aishwaryanr/awesome-generative-ai-guide/blob/main/interview_prep/roles/forward-deployed-engineer/resources.md)（P22）。问题文件实际包含 99 个展开项、10 个分组。

**它是作者编写的备考资料，不是已核验的候选人亲历面经，也不是 Palantir 官方标准。** 我们未把其中轮次权重、通过率或建议答案当作事实。其资源列表只用于寻找原始来源；链接存在不等于原文已阅读。

最适合本产品的部分是第 85–90 题的模糊问题拆解，以及第 91–99 题的客户沟通情境。以下是题材的用途及本项目改写：

| 情境 | 本项目如何改为访谈与评测 |
|---|---|
| 物流看板不可信 | 让用户区分状态缺失、更新滞后、标识冲突、责任不明；回答释放不同新证据 |
| 三个遗留系统的标签不一致 | 问同一对象如何关联、由谁定义口径；避免直接推荐“再上一个平台” |
| 公共服务响应时间指标 | 要求分清时间起止、事件类别、地区和异常；防止只优化平均数 |
| 客户要求两周内交付复杂功能 | 确认硬期限对应的业务原因与最小可用范围，而非盲目承诺 |
| 要求 RAG 达到 100% 准确 | 确认错误类型、影响与人工复核；不能承诺检索消除所有错误 |
| 安全团队拒绝生产凭据 | 问可接受的受控样本、权限和审批；不建议绕开安全团队 |
| 客户坚持既定架构 | 先问架构背后的限制与已投入成本，再讨论最小验证 |
| 之前 AI 项目失败，客户不信任 | 请其讲最近一次失败与后续处理，分清技术、采纳、维护和承诺失配 |
| 高影响场景想完全自主行动 | 确认动作、可撤回性、授权、监测和接管责任，必要时联合专家 |
| 内部团队担心被替代 | 确认实际担心的责任和工作变化，不把阻力当成需要强行推动的证据 |

这类材料的价值主要是提供**会使方案收缩的情境**，而不是提供可直接套用的回答。实际产品应记下“什么回答会改变路线”，而非告诉模型“这道题标准答案是什么”。

目前官方 Palantir 面试博客已找到链接但未获得正文；少数个人网站返回安全检查，不能声称已经读过。后续重点补足有完整追问记录、失败反馈和作者背景的第一人称材料，而不是继续堆同质题库。

## 7. 阿福研究：能借鉴什么，不能声称什么

### 产品层

应用发布方在应用宝的说明列出健康咨询、图片解读、健康档案及医疗服务衔接。这支持把它看作持续健康交互与服务入口的产品参照，不能证明任何诊断准确率或医生规模。见 [发布方应用说明](https://sj.qq.com/appdetail/com.antgroup.aijk.android)（A11）。

本项目可借鉴的体验是：按用户的问题进入、解释关键信息、允许提供材料、形成连续记录，并在需要时把用户交接给对应专家。这里的企业产品方案是我们的推演，不宣称复现其内部架构。

### 技术与效果层

主报告已区分开源医疗模型、GAPS 评测和阿福在线系统。额外需要注意开源仓库的版本差异：[MedicalAiBenchEval README](https://github.com/AQ-MedAI/MedicalAiBenchEval)（A08）对 GAPS 缩写和安全评分的描述，与论文 v2 并不完全一致；本次只读说明，未审计全部代码。复用前需要逐项对照论文、版本、测试和实际实现。

“超过医生”还应区分任务场景。另一个项目 AMIE 的论文摘要报告了 149 个标准化场景、20 名基层医生参与的文字对话比较，并明确提示这不是通常临床实践，仍需更多研究。**它不是阿福，也不能证明消费应用在现实诊疗中全面优于医生。** 见 [Towards Conversational Diagnostic AI](https://arxiv.org/abs/2401.05654)（A12；本次阅读摘要，未阅读全文）。

企业分诊同样如此：合成案例得分、专家意见一致、真实业务获益，是三个不同结果。系统需要同时保留评测、专家复核和后续验证，不能用其中一个替代其他两个。

## 8. 公开经验不够时，怎样把专家的判断过程问出来

公开内容常省略失败、实际成本、组织冲突与判断改变的时刻。下一步最有价值的研究不是写更多泛论，而是**复盘专家真实处理过的一件事**。以下是本项目提出的专家访谈协议，受到本地课程第 05、14、18 讲和上述原始访谈的启发，不是已经验证的标准方法。

### 8.1 一次复盘只围绕一个案例

尽量选择能回看材料的已完成案例，隐藏企业身份和敏感细节，确认哪些内容可用于产品知识。成功与失败都收；优先记录实际步骤，不要求专家先概括“FDE 的十条原则”。

| 步骤 | 对专家问什么 | 需要产出的判断数据 |
|---|---|---|
| 初始请求 | “客户最初怎么说？当时为什么找你？” | 原始诉求、角色、背景 |
| 第一印象 | “你最先怀疑什么？当时还不知道什么？” | 初始假设与未知 |
| 现场还原 | “第一次会谈你先问哪一件事？接着为什么问第二个问题？” | 实际提问链与理由 |
| 关键转折 | “哪一个回答、文件或观察，让你改了判断？” | 新证据、旧结论、新结论 |
| 反证与选择 | “什么信息让你排除其他解释？考虑过哪些便宜办法？” | 竞争解释、被排除路线与条件 |
| 共同确认 | “如何确认你理解对了？谁不同意？怎样处理分歧？” | 对齐动作、角色冲突与结果 |
| 不确定性 | “哪些事直到最后也不能确认？你怎样向客户表达？” | 可说与不可说的边界 |
| 服务范围 | “为什么需要你？换成标准软件、内部团队或另一类顾问会怎样？” | FDE 的独特作用与替代路径 |
| 后续结果 | “三个月后发生什么？维护者是谁？哪些效果没有兑现？” | 结果、采纳、成本与局限 |
| 反事实 | “如果客户当时的某个关键回答相反，你会如何调整下一问和建议？” | 可用于分支评测的条件 |

不要把专家的事后解释自动视为当时的真实思路。能回看会议记录、交付物版本和反馈时，优先交叉核对；无法核对的保留为口述经验。

### 8.2 从专家案例生成可审阅的最小卡片

```text
情境：企业提出一个 AI 技术方案，但实际痛点未确认。
初始假设：模型能力不足／数据不齐／例外规则与责任不明。
决定性问题：最近一次失败事件，在哪一步必须找负责人临时决定？
关键回答：规则本身存在但无人有权确认例外，数据不是主要阻塞。
判断变化：从模型改造转向权责与例外记录对齐。
适用边界：该判断只适用于这类证据；若例外可稳定计算，需要重新评估。
用户确认：实际操作者与业务 owner 是否认可事件还原。
来源：专家口述／会议材料／产物版本，分别登记。
评测：改变关键回答，Agent 是否相应调整下一问和服务路线？
```

这是合成示例。真实卡片必须保存来源、原始定位、专家修订及使用范围。

### 8.3 验证最有价值的不是“听起来像专家”

请独立专家看同一企业情境，先独立给下一问和暂定判断，再对照讨论分歧。区分目标差异、事实遗漏、行业经验不同和价值取舍；不要把多数票当成因果真相。随后回访真实用户，检查材料是否能够拿到、问题是否容易回答、建议是否改变实际投入。

将一次专业能力更新落实为：**来源卡修订 → 问题卡分支修订 → 旧建议重新检查 → 回归案例增加**。这个循环完全可以不训练模型。

## 9. 下一批资料该补什么

与其先追求数量，优先补四类空白：

1. **明确“不该做”的真实案例**：FDE 如何拒绝项目、推荐标准工具、缩小范围，最终是否验证判断。
2. **未成功的企业落地**：没人用、数据无法关联、业务 owner 退出、维护成本失控，具体在哪一问能提前发现。
3. **跨角色对齐记录**：老板、操作人员、IT、财务对同一事件的不同解释，以及如何形成共同范围。
4. **高影响领域的具体边界**：由行业与安全专家审核的控制、责任和交接条件，避免用泛化“合规重要”代替专业细节。

本轮已有的公开资料足以起草提问协议和分流规则；要成为真正可信的专业产品，仍需要这些带证据和结果的专家案例，以及真实用户多轮验证。
