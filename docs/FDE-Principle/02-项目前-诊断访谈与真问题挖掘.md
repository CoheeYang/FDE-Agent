# 02 项目前 Ⅱ：诊断访谈与真问题挖掘（核心篇）

阶段目标：从「嘴上的需求」挖到「可衡量的真问题」。这是 FDE 与外包/销售的分水岭，也是 FDE-Agent 产品的主战场。子阶段：开场 → 事件还原 → 例外挖掘 → 目标与数字 → 数据与权限 → 竞争假设 → 三次收口 → 冲突与纠错。

## 2.0 访谈总纪律（先于一切技巧）

- **原则：越过两层陷阱**。①客户嘴上说的需求往往是他自己想出来的**解决方案**；②你眼里客户的「问题」可能是人家基于业务的**合理选择**。两个陷阱都要用追问破。`[课程]`
- **原则：每轮访谈最终要回答六个问题**（发生了什么/要改善什么/必须保留什么/还不知道什么/下一步问谁/何时重看）。`[主研究文档 §5.1，本项目设计]`
- **中性原则**：问题必须中性、可回答、不诱导——不诱导用户认同「必须请 FDE」，不让不懂接口的人回答接口问题。诱导来的认同会在验收时反噬。`[主研究文档 §13.2 + 外部·已核验：GOV.UK D01 深度访谈规范]`
- **数字必须带定义**：出现任何数字，追问分母、时间窗、统计者、口径（销售 GMV ≠ 财务 GMV）。`[主研究文档 §6.2]`

## 2.1 开场（前 3 轮）

- 开场目标：建立「围绕一个真实事件谈话」的框架，而不是收集企业档案。`[主研究文档 §5.2]`
- 角色与范围先行：受访者是谁、观察范围多大、多个诉求哪个优先（问题卡 Q002/Q003）。`[内部问题卡]`
- **原则：从模糊技术诉求拉回具体业务事件**——「最近哪次（销售决策/生产异常/交付延误）因为缺信息或处理太慢出了问题？」`[外部·已核验：微软 D12 追问链，本项目转写]`
- 用户给出现成方案时（「做个 RAG / 上个大模型」）：“如果现有工具能解决大部分，哪里仍然过不去？"——先排除便宜替代。`[外部·已核验：微软 D12]`

## 2.2 事件还原（五天摸底的动作，访谈版）

- **原则：问「上周二下午三点你在忙什么」，不问「你们一般怎么做」**。前者得到真实发生的事实，后者得到被整理过的标准流程。`[课程·3.1]`
- **原则：亲眼看一遍真实工作流程 > 一百场汇报**；「真正的用户」不是他的主管——主管描述的是组织架构图上的理想版。听不懂本身就是信号：它测量了你以为的业务和真实业务之间的距离。`[课程·3.1]`
- 自己当小白把这活干一遍（定硬目标）；姿态越资深越要拜用户为师——对方才会讲不好意思对领导讲的细节。`[课程·3.1]`
- **Palantir 四问（Data/Logic/Action/Security）围绕同一事件穿起来**`[外部·已核验：Palantir P14 Ontology 文档，本项目转写为问法]`：
  - Data：做那次决定时看了哪些信息？哪项直到最后也没法确认？
  - Logic：最后为什么选这个办法？正常规则与例外由谁解释？
  - Action：决定后谁在哪个系统改了什么？哪些人还要手工接着做？
  - Security：谁有权批准？做错能否撤回？谁能发现和接管？
  - 边界：四问服务一个决策闭环，**不要**做成全企业架构调查（会诱导客户购买庞大平台）。
- 「最小业务地图」：一次异常 → 两处信息 → 一个规则判断 → 一次批准 → 一个结果记录。能共享并复查这个闭环，才有资格谈扩展。`[主研究文档 §3 转写]`

## 2.3 例外挖掘（「奇怪的星期二」）

- **原则：专门挖没人主动说的阻塞点**。问法：上次出大问题是什么时候？有没有每隔一阵来一次、特别烦又躲不掉的怪情况？月底/大促时流程变成什么样？`[课程·3.1]`
- 正常流程听起来很顺 → 追问高峰、月底、例外；资料只含正常日 → 要高峰日样例（问题卡 Q011/Q013）。`[内部问题卡]`
- 关键员工依赖（Q014）、无意义环节（Q010）都是例外入口。`[内部问题卡]`
- **发现「看起来不对」的做法，先问「你们为什么这么做」**——很多是业务沉淀的 know-how，不是 bug。识别 know-how 与通用知识的差异是 FDE 最大价值，也最容易翻车。`[课程·3.1]`

## 2.4 目标与数字（北极星三条件）

- **原则：把「动作」翻译成「结果」再谈方案**。「帮我投广告」（动作）→「以可持续 ROI 打开新增长渠道」（结果）。动作照做不难，**结果成不成立需要证据**。`[课程·3.2]`
- 北极星三条件同时满足`[课程·3.2]`：与商业价值强相关（GMV 不是 UV）；能通过自身努力影响（排除天气/位置主导的指标）；可拆解可归因（拆流量×转化，暑假撑大的是流量不是转化）。
- 选定指标立即两步：**历史数据建基线**（没基线分不清自然增长）+ **归因口径白纸黑字写进立项文档**（验收不扯皮的前提）。`[课程·3.2]`
- 省工时 ≠ 现金收入：追问省下的时间用在哪、是否真有增量业务可承接（可兑现性三问，Bain 迁移）。`[外部·已核验：Bain D16，本项目转写]`
- 用户给「提效/降本」但成果口径不清（Q015–Q017）：先锁口径再谈价值。`[内部问题卡]`

## 2.5 数据与权限（筛组织的实操版）

- 数据访问按「只读→样本→受控环境」阶梯谈，不把「现在给不了生产权限」直接判死——准备度不足 ≠ 必要性不存在。`[主研究文档 §9.1]`
- 数据地基三问（制造业口径，可泛化）：指标能否追到源系统？实体能否跨系统对齐？老师傅的 Excel 进系统了吗？`[课程·行业篇]`
- 「提问者看不到的数据，Agent 也不能替他看到」——权限继承是产品红线，访谈期就要确认权限模型。`[课程·4.4]`

## 2.6 竞争假设（鉴别诊断——本产品最核心的专业能力）

- **原则：不要单假设推进，维护≥2个竞争解释并逐一找区分证据**。现象「交付变慢」的解释可以是订单复杂度/数据延迟/资源冲突/例外规则/操作能力——「最近一单等待主要发生在哪里？同期改变了什么？」`[外部·已核验：Bain D17 推导结构，本项目转写；主研究文档 §6.1]`
- 每个假设记录：支持证据、反证、尚需验证的**区分条件**；不伪造概率——没有数据就标未知。`[主研究文档 §12.1]`
- **用户把问题归因于模型/技术时（Q019），优先检验组织与流程解释**（权责、例外规则、口径冲突）——中国 ToB 的病根常是「标准的软件撞上不标准的流程」。`[课程·7.1 + 内部问题卡]`

## 2.7 三次收口（对齐）

1. **收口事实**：发生了什么——复述事件、角色、影响，请用户纠正。`[主研究文档 §8.1]`
2. **收口目标**：要改善什么、必须保留什么约束、可投入什么。`[§8.2]`
3. **收口判断**：暂定方向、依据、未知——明示哪些是用户陈述、哪些是推断。`[§8.3]`

确认模板（最小文本）：「我理解我们要改善的是【某角色在某情境下的某项决策】，影响是【有口径的影响】，基线是【…】，成功是【可观察变化】，约束是【…】，仍不能确认【未知】。对吗？有没有理解错或漏掉的？」`[外部·已核验：微软 D12，本项目转写]`

## 2.8 冲突与纠错（访谈的诚实性）

- **矛盾出现时不要强选一个答案**：记录矛盾双方、来源轮次，设计能区分两者的下一问；把「同一事实在不同人处说法不同」本身当作发现（口径/权责问题线索）。`[主研究文档 §8.4]`
- **用户纠正（金额/口径/责任人）后，相关判断必须撤回重建**——只改字段不重检判断 = 伪纠错。这是 Agent 评测的纠错题蓝本（[方案A §3](../benchmarks/方案A-能力基准-FDE-GAPS.md)）。`[主研究文档 §13.2]`
- 用户说「不知道」是合法回答：换可回答的问法或标记待补证，不许逼答。`[GOV.UK D01 迁移]`

## 2.9 角色与行业分支（追加问题维度）

- 同一事件向不同人问不同问题：老板问经营影响与决策链；操作者问具体步骤与例外；IT 问系统与权限；财务问口径。`[主研究文档 §7.2]`
- 行业问题围绕业务事件与失败代价：金融问合规与控制权；制造问良率/报废的真实数字与源系统；能源问非生产时间与安全；零售客服问拦截率口径与转人工。`[课程·行业速查表 §7.3]`
- 行业篇总纲：**「行业只是变量，方法才是常量。」**案例数字只能帮判断量级，不能变成对自己项目的承诺。`[课程]`
