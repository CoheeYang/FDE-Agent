## 0. 全局心智模型（先读这一节）

**一句话总纲：AI 负责做出来，人负责判断做得好不好。写代码不再稀缺，把 AI 交付成客户的业务结果、再把现场认知沉淀回产品，才稀缺。**

### 四个基本判断（全课骨架）

1. **需求与能力同时被点燃**：企业 GenAI 投入约 95% 回报为零（MIT），88% 的 POC 进不了生产（IDC）。瓶颈不在模型，在"最后一公里交付"——交付从后端环节变成了胜负手。
2. **判断真假 FDE 只看一件事**：现场得到的认知，有没有回流到产品里。最朴素的检验是"第二个客户做的时候，是不是比第一个更容易"——永远十个人三个月，那就是高级外包。
3. **先找真问题，再谈 AI**：具体工具会过时，"别拿着锤子找钉子"不会过时。
4. **真正复利的资产是机制**：前线怎么发现问题、现场经验怎么回流产品、客户怎么逐步接手、下一个项目怎么复用——这套机制才是组织的核心竞争力。

### 三个贯穿全程的框架

| 框架 | 内容 |
|---|---|
| **人机分工** | AI 做：学业务、挖证据、搭 demo、写代码、整理纪要、起草文档、对照日志查数据不一致。人判断：哪个是真问题、方向对不对、红线在哪、什么算验收、怎么定价、该不该对客户说"不" |
| **Delta–Echo 双循环** | 内环（在客户现场把东西做出来）让客户满意；外环（把单客户成果固化成产品能力）让公司值钱。只有内环没有外环 = 套着软件外壳的咨询公司 |
| **三层"好"** | 业务层北极星指标 → 系统层评估集 → 行为层真实使用。三层都算好，AI 项目才能有价值地被验收 |

**客户验收标准的三级跃迁**（中国市场的演进，也是本 SOP 的主线）：装好系统 → 做完项目 → **跑出效果**。

### 参考交付节奏（Anthropic 应用 AI 团队剧本）

第一周：8–15 场用户访谈、嵌进业务 → 第二周：设计评估集 → 第三四周：搭 Prompt 与 Agent → 第五周：灰度上线 + 培训客户内部 champion → 之后边用边复盘迭代。一个周期约 5–6 周。

## 1. 项目生命周期 SOP 总览

| 阶段 | 核心目标 | 关键动作 | 硬交付物 | 最容易死在哪 |
|---|---|---|---|---|
| ① 售前 | 用"结果"吸引客户；筛掉不该接的项目 | 效果定价方案、demo 造信任、"治理即产品"入场券、双向筛选八问 | OLA / 合同（含客户配合义务、退出条件） | 过度承诺埋下 demo 债；接了无预算、无赞助人的项目 |
| ② 进场调研（≈第 1 周） | 摸清"真问题" | 五个动作摸底、真问题五条判断、干系人地图 | 真实流程图 + 干系人地图 | 把嘴上需求当真问题；把自己的想当然当客户的问题 |
| ③ 场景与初步方案（≈第 2 周） | 选对第一个场景；与客户共同定义"好" | 需求翻译、北极星三条件、基线与归因、打分排序、MVP+MVA demo | 用例优先级表 + 能跑的 demo + 评估集初稿 | 场景不可衡量/不可归因；demo 宽而断 |
| ④ 落地迭代（施工期） | 每周可见的真实进展 | 每周 demo 纪律、gap 四象限、代码三区、集成三动作、评估驱动开发 | 生产代码 + 评估集 + 每周一页纸 | 集成（沉默杀手）；"考不过就改考卷"；负债区写死代码 |
| ⑤ 上生产 | 让 CIO 放心 | 六项上线检查、灰度、五类风险责任人表、HITL 分级 | 上线检查清单 + 风险责任人表 + 演练过的预案 | 跳过"硬化"阶段；预案没演练；权限护栏缺失 |
| ⑥ 收尾与复利 | 客户接手、公司沉淀 | 自治阶梯交接、结项沉淀清单、五步复盘、私有知识入库 | 一页复盘纪要 + 平台提交 + 知识资产 | 只复盘不沉淀；定制无法"毕业" |

## 2. 阶段一（项目前·售前）：如何吸引客户

### 2.1 底层逻辑：客户为结果付费，不为工具付费

- 中国老板很难单纯为"平台/系统"付费（听着就是成本），愿意为**结果、增长、"你把这件事整个替我做了"**付钱。预算层级：营销类预算比 BPO 人力外包预算高一个数量级，又比 IT 采购类预算再高一个数量级——客户一直在用预算把供应商从"卖产品"推向"卖结果"。
- 中国 To B 传统交付三宗罪，恰是售前方案的突破口：**价值难衡量、责任无法界定、风险全在客户**。客户压价、要定制、要私有部署、拖尾款，本质是风险错配下的理性自保——方案若能主动解决风险共担（基线 + 归因 + OLA），就在低价竞争中形成差异化。
- RaaS（按结果付费）示例：约定复购 GMV 基线 1000 万 → 承诺做到 1200 万 → 超出基线的**增量**收 10%；没有增长不收效果分成，客户原有盘不受损。

### 2.2 吸引客户的四个抓手

1. **用能跑的 demo 代替一百页方案**（形态要求见 §4.4）。方案说服不了客户的三个原因：方案是抽象的，客户脑补的与你想的可能不是同一个东西；对方案表态成本极低（"挺好的，继续推进"毫无承诺）；AI 时代方案里的 AI 永远聪明，demo 里的 AI 才会犯错——客户要亲眼看到它怎么表现、怎么出错，才能建立真实预期。
2. **敢说"不"**。课程真实案例：客户带预算来要求投 Google Ads，FDE 三层调研后交付的核心建议是"**建议不投**"（该业态获客是发现型/推荐型路径，头部竞品付费搜索流量占比均 <5%，用户决策前 60% 以上的信息收集发生在社区帖与垂直目录站），同时给出"渠道决策矩阵"：该全力做什么、该延后什么、各附证据与理由。结果：客户更信任了。"放弃某个场景，和看衰某个客户，是两回事"；写"放弃"必须同时给出更好的替代。"**敢不敢写'放弃'，是检验你在做 FDE 还是在做外包的试金石。**"
3. **治理即产品（强监管行业的入场券）**。金融/政企/医疗客户买的不只是合规，而是**控制权**：模型和数据在哪里运行、代码由谁掌握、关键决策由谁作、出了问题能不能追溯。三笔账：**预算账**（治理投入可以单列报价，不必与功能开发抢预算）、**采购账**（合规部门是治理能力的直接使用者，越早参与方案与预算评审，越可能成为内部支持者）、**规模账**（一个客户的审计要求、审批流程沉淀成配置与模板，复用给同类客户）。"业务部门买功能，合规部门买'出了事说得清'。"
4. **选对战场再承诺**。a16z 四条件：问题足够关键（动辄数亿美元损失，而非后台流程提效 10%）、客户足够集中（几十家超大客户撑得起嵌入式工程）、客户间有共同模式、场景有足够强的数据/集成/监管门槛。客单价-模式匹配：几十万 → 轻 FDE（标准产品+行业模板，远程为主）；几百万 → 中 FDE（关键场景驻场，基础费+效果分成）；数千万以上 → 重 FDE（全周期嵌入，深度对赌）。**最昂贵的错配：拿几十万客单价维持全周期驻场重 FDE——"用咨询公司的成本结构，赚软件公司的钱"。**

### 2.3 售前筛选：双向过滤八问（进场之前必须全过）

**立项四问（筛项目）**：
1. 客户那边有没有一个真正说了算的负责人？
2. 有没有真实的预算？
3. 用什么指标衡量成功？
4. **有没有明确的退出条件？**——"一个没有退出条件的项目，不是项目，而是一份无底洞式的支持合同。"

**客户四问（筛组织）**：
1. 有没有一位真正有分量、愿意带你进业务会议的人？（没有他，连真实工作流都看不到）
2. 真实的数据和权限给不给？哪怕从只读开始。（给不给权限，最能看出客户愿不愿意为合作改变自己）
3. 反馈周期多长？（建议发出去一个月不知对错，FDE 的迭代优势归零）
4. 谁为探索买单？（进场头几周产出只是"把业务学明白了"，合同能否容忍这段不确定期）

> 八问中任一问明确否定，就别硬进场。**"外包的客户不用改变自己，FDE 的客户必须改变自己"**——FDE 模式的成立本质上是一场双向筛选。

### 2.4 合同与定价要点

- **OLA（结果级协议）四要素**：①这次交付要产出什么结果；②怎么衡量（北极星指标+基线+归因，最好精确到计算公式，用客户业务语言写，不用 FDE 黑话）；③谁对衡量负责（借干系人地图落到具名负责人）；④审核节奏（按指标变化周期定）。OLA 的本质不是供应商的记分卡，而是建立信任的机制。
- **推荐收费结构：基础费 + 效果分成**。基础费为探索期和最低交付投入设底价（覆盖人力与 token 成本），效果分成分享上行收益。应对客户质疑"凭什么增量分你 10%"：只从增量产生、原有 1000 万不受损、没有增长就不收——谈完后，讨论会自动从"该不该分"转到"基线和归因怎么定"。
- **合同必须写客户配合义务**：谁提供数据和权限、谁推动流程调整、谁什么时间做决策给反馈；客户未履行，不能全算供应商头上。
- **敢接效果对赌的供给侧前提**：外环沉淀到位（第二客户成本降到零头）+ 知识资产化 + Agent 让陪跑可复制。"**沉淀没做到位就去对赌，那不叫商业模式创新，那叫赌博。**"
- **商业账纪律**：三类投入分开算（首客户探索 / 后续重复交付 / 平台工程）；早期不只盯毛利率，看总毛利与产品能力是否增长；毛利让出去必须换回三样东西——可复用的产品能力、客户的数据入口、成为客户日常工作离不开的系统。三条边界任何一条长期不成立（总毛利不增长/同类项目成本不降/现金撑不到转折点），就不是在投资产品，而是在补贴服务。

### 2.5 本阶段客户洞察

- 老板的决策常是"会议驱动"的：demo 惊艳当场拍板、预算到位——验证的是演示价值而非业务价值。售前的责任是主动管理预期：**在 demo 阶段就主动暴露长尾和脏数据**，当场跑几条真实烂数据、展示兜底方案。"现在暴露的成本是一点面子，上线后暴露的成本是信任甚至赔偿。"
- 客户不缺又一个通用平台，缺的是"有人帮我把自己那摊具体的事跑通"。
- 强监管行业客户可暂时不上 AI，但系统进生产环境的治理要求不是可选项；他们有明确的合规预算与较强付费能力——**监管越严的行业，越是 FDE 的主场**。
- 关系在前，解决在后："中国 to B 的本质，是甲方和乙方关系挺好，而甲方有个问题恰好乙方能解决，于是让乙方来解决。"

## 3. 阶段二（项目前·立项）：进场调研与初步方案

### 3.1 五天摸底 SOP（进场第一战）

**总原则（越过两层陷阱）**：客户嘴上说的需求往往是他自己想出来的**解决方案**，只能信一半；你眼里客户的"问题"，也可能是人家基于实际业务的**合理选择**。

**五个动作（Five-Day Discovery）**：

1. **坐到真正的用户旁边，画出真实流程图。** 是"真正的用户"不是他的主管——主管描述的是组织架构图上的理想版本，真正干活的人手上跑的是另一套。"听不懂"本身就是最强的信号：它告诉你真实的业务和你以为的业务之间隔了多远。
2. **把自己当小白，亲手把这活干一遍。** 定三个硬目标（示例：能跟投手顺畅聊专业话题；能在真实复杂场景下完整做一次上架；能每天独立完成盯盘），自己开户、自己投钱学。姿态上越资深越要放低、拜用户为师，对方才会把最真实、甚至不好意思说给领导听的细节讲给你。
3. **用合成数据搭轻原型，去"挑逗"真实反应。** "人对着空气是说不出真需求的，但人对着一个具体的东西，意见就会冒出来。"哪怕很粗糙，扔到用户面前，他会脱口而出"这个不对""我们从来不这么干"。驻场的录音、访谈记录、碎片信息交给 AI 校对、留档、提炼反复出现的卡点——哪条是真痛点、哪条是情绪宣泄，由人逐条判断。
4. **专门去挖"没人主动说"的阻塞点。** 问刁钻问题：上次出大问题是什么时候？有没有每隔一阵就来一次、特别烦又躲不掉的怪情况？月底、大促时流程会变成什么样？更好的问法：**别问"你们一般怎么做"，问"上周二下午三点，你手头上在忙什么"**——前者得到被整理过的标准流程，后者得到真实发生的事实。盯住"奇怪的星期二"：没人写进文档、每隔一阵来一次、操作员花二十分钟摆平、从不在正式场合提起的怪情况。办公室问不出的，饭桌上、电梯里聊得出来。
5. **分清"真问题"和"客户的合理选择"。** 发现"看起来不对"的地方，先别急着改，老老实实问一句："你们为什么这么做？"很多答案是：这不是 bug，是业务实践中积累的 know-how。识别 know-how 与通用知识的差异，恰恰是 FDE 最大的价值所在，也最容易翻车。

**真问题五条判断标准（逐条过）**：
1. 它可衡量吗？落不到具体数字或业务结果的，先放一放。
2. 是用户亲历的问题，还是主管转述的？转述的打个问号。
3. 你亲手验证过它真实存在吗？没验证过的先存疑。
4. 你排除了"它其实是客户的合理选择"吗？没排除的，回去再问一句为什么。
5. 解决它价值够大，而且**能归因到你头上**吗？（进入场景选择）

### 3.2 场景选择 SOP：把"嘴上的需求"翻译成"可衡量的结果"

**为什么 AI 时代不一次把系统建起来**（传统 To B 一两年大交付的三个不成立）：AI 的效果是试出来的不是设计出来的；AI 项目本就九死一生，还赌一两年见分晓风险不合理；基模每 3–6 个月大进步、客户业务也在快速变，长周期系统做到一半就落伍。"**系统不是坐在办公室设计出来的，是从一个场景一个场景中长出来的。**"

**第一步：翻译。** "帮我投 Google Ads"（动作）→"以可持续、可盈利的 ROI 打开一个新的增长渠道"（结果）。动作永远可以照做，把钱花出去一点都不难；**结果成不成立，需要明确的证据**。

**第二步：北极星三条件（必须同时满足）**：
1. **与商业价值强相关**——指标涨了生意要真的变好（GMV，不是 UV/PV）；
2. **能通过自身努力影响**——线下生鲜 O2O 把门店总销售额定成北极星，但大头由位置、天气、季节决定，线上运营影响微小 → 不能选；
3. **可拆解、可归因**——旅游 App 总间夜量涨了，但正逢暑假 → 拆成流量×转化率，优化效果落在转化率，暑假撑大的只是流量，两笔账分清。

   选定指标后立即两步：**用历史数据建基线**（效果讲增量，没基线分不清自然增长）；**归因口径白纸黑字写进立项文档**。做在前面，验收不扯皮。

**第三步：到价值链上找场景。** 需求收集会只会选出"嗓门最大、职级最高"的需求；正确做法是把客户整条价值链摊开，顺着链条看时间和钱耗在哪里。标杆案例：OpenAI FDE 进半导体制造商，画完整条价值链发现工程师 70–80% 时间花在修 bug → 选"缺陷验证"为目标场景，交付含 debug Agent 在内的十个用例，效率提升 20–30%，下一目标 50%。

**第四步：打分排序。** 五个维度：**价值、可行性、速度、风险、被采纳的可能性**（最后一个最易被技术人忽略——方案再好，一线不愿用，或动了哪位领导的奶酪，就推不下去）。产出**用例优先级表**，三档：**做**（排先后顺序）/ **延后**（写清楚什么条件下重启评估）/ **放弃**（明确写上放弃及理由）。这张表把"为什么先做这个不做那个"从口水仗变成有证据可追溯的文档。

> "你只有一次用最小成本撬动最大信任的机会。"敢写"放弃"，客户反而更信任你——他知道你推荐"做"的场景，是用同一套证据标准筛出来的。

### 3.3 干系人与信任 SOP

**画干系人地图**（进场后尽早）：每人四问——**他能拍板什么？能否决什么？需要知道什么？以及最重要的，他真正在意什么？**（动机栏最易被忽略；老板在意经营指标、IT 负责人在意系统安全与团队话语权、一线在意活会不会变多岗位保不保得住——方案要对每一种"在意"都有交代。）**写真名，不写部门**；每个名字都来自真实对话，不是照组织架构图想象。

**三类关键人，三种打法**：

| 类型 | 典型角色 | 打法 |
|---|---|---|
| 能**杀死**项目的人 | 预算与权力持有者（随时能说"先停一停"的高管） | 低频但高质量同步：让他每次想起项目，脑子里都是清晰进展+可控风险 |
| 能**拖延**项目的人 | 流程把关人（安全、合规、采购） | 提前送材料、尊重其专业性、把流程时间留足，别到节点才堵门 |
| 能**放大**项目的人 | 标杆用户（用得好、有影响力、别人信服） | 重点服务，让他先用出效果，再主动传播，双赢 |

**怀疑者转化**：每个漫长的企业项目都有一个（觉得 AI 是炒概念的资深工程师，或被上一家供应商坑过的业务骨干）。使劲说服 → 姿态成推销；绕开他 → 他在暗处持续反对。第三种做法：**给他一个真实的角色**——请他当第一个测试者，把系统的一部分交给他用最挑剔的眼光来测；他挑的毛病认真修，他验证的效果他自己确认。系统一旦是怀疑者亲手验证过的，他往往变成项目最强的内部拥护者——他的专业和较真，从阻力变成了质检。

**赞助人管理**：赞助人（通常为发起项目的高管）会消失——升职、调岗、离职、失势。两条预防：①从一开始就培养**至少两个赞助人**；②尽快建立**自下而上的真实使用**——一线员工每天离不开你的系统时，换领导也难拔掉。"只有单一赞助人的项目，签单的时候有多顺，崩塌的时候就有多快。"

**汇报纪律**："在客户现场，汇报本身就是交付的一部分。"
- 金字塔原理：结论先行——先一句话说结果，再两三条理由，最后才是证据。周报反例："完成了数据接入、跑通测试环境"是过程记录；"上线时间不变，效果达预期，但有一个数据权限风险需要您推动"才是决策者要的。
- MECE：像设计接口一样设计表达，不冗余、不遗漏。
- 同一座金字塔对不同人讲不同深度：电梯里讲塔尖一句，周会讲理由，技术评审才下沉到证据。
- 技术语言→业务语言的翻译必须 FDE 自己干："你不翻译，就会有别人替你翻译；翻译错了，代价还是算在你的项目头上。"

**信任边界（信任 ≠ 顺从）**：拒绝**接单员陷阱**（来一个需求接一个，从专家降级成一双手）；拒绝**永久拐杖**（客户永远离不开你=双输）；信任是一段谱系，靠一次次兑现承诺往上走。

### 3.4 初步方案的形态：能跑的 demo（MVP + MVA）

- **三物区分**：原型对内（可省页面、可写内部术语）；demo 对客户——数据可合成，但**场景、术语、操作路径必须是客户未来真正要看到和理解的**。
- **最小单元原则**：端到端，**宁可窄，不能断**。演示报表自动化：选一张最有代表性的报表从取数、配置、计算、可视化到结论完整跑通一条线，而不是十张报表每张只做一两步。窄而通 → 客户觉得"这事能成"；宽而断 → 客户只记住"到处都是半成品"。
- **双重验证**：MVP（面向客户，回答"值不值得做"）+ MVA（最小可行架构，面向工程，回答"做不做得成"）。MVA 不是一次性脚手架，是能长成生产架构的种子——建不好，第四个月就得重写。MVA 先立**三根承重柱**：①换客户真实数据后，模型准确率到不到业务可接受的下限；②模型需要的数据和工具接不接得通（鉴权、接口、权限、网络隔离）；③真实业务规模下延迟、并发、token 成本能否接受，出错有没有兜底。
- **节奏**：第一周驻场结束 → 周末用 AI 把高保真 demo 搭出来 → 第二周带回客户现场。动手前习惯性先问："这个问题真的需要 AI 吗？"

### 3.5 本阶段客户洞察

- 客户告诉你的常常不是问题，而是他自己想出来的解决方案；最有价值的阻塞点没人主动说，因为大家习以为常。
- FDE 是被空投进"潜在敌对组织"的外来者：项目会改变一些人的工作方式和利益，有人盼你成，也有人盼你不成；要克服的多是政治、官僚与组织障碍，而非技术障碍。
- **政治是双向的**：自己公司内部同样有政治（资源给不给你、产品团队接不接你的需求）；把"自己人"也画进地图，同样分能杀死/能拖延/能放大三类。

## 4. 阶段三（项目中）：落地与迭代

### 4.1 迭代引擎：每周 demo 纪律

- demo 的第一作用不是让客户说"哇塞"，而是**让客户说"不对"**——"人对着文档提不出真意见，人只有对着能跑的东西才会说真话。"
- 每周给干系人演示；每次演示必问："**要怎样，你才会点'同意'？**"——把讨论从"你觉得怎么样"（收获客气话）拉到"距离你验收还差什么"（收获具体改进清单）。"我说不好，感觉不太对"没法拿回来改产品；"审批人的名字应该放第一列"就是可排期的工单。
- **每次 demo 记三样东西（一页纸，每周都有）**：
  1. 当场的具体反馈 → 直接变工单；
  2. 没说出口的迟疑 → 哪个功能他明显不感兴趣、哪个环节反复追问——这些信号比客气话更诚实；
  3. 双方的承诺 → 客户答应给的数据、你答应改的功能，各自落到具体的人和时间。
- 演示尽量现场做（能看到谁凑过来、谁小声议论、谁忍不住想试）；演示前让 AI 扮演客户角色从头走查一遍。
- 前提：客户反馈能当场给、当周给——否则每周 demo 退化为每周汇报。跑不动每周 demo 的团队，到第四周就会陷入双方拿 SOW 逐条抠字眼的规格争论。
- 保持清醒三条：①demo 通过 ≠ 活儿干完，后面有最容易被砍掉的"**硬化**"阶段（边界情况、监控、压测、回滚）——跳过它省下的时间，会在六个月后系统第一次真出故障时用信任加倍还回去；②警惕 **demo 债务螺旋**——demo 允诺的体验生产撑不住，之后每次接触都背着期望债；"demo 赢来的不是合同，而是继续往下走的资格。"

### 4.2 施工三问

**第一问：先做哪个 gap？**（gap = 产品现有能力与客户真实需求的差距）
两个坐标：通用 vs 特有；阻塞 vs 增强。

| | **阻塞上线** | 不阻塞 |
|---|---|---|
| **通用需求** | 平台层优先做——这家客户解决，下个客户直接受益 | 不在项目里顺手做：走"平台提交"，进正式需求池统一排期 |
| **特有需求** | 要做，但做在隔离层，别让这家客户的特殊逻辑渗进产品主干 | 与客户商量延后，甚至明确说不做（写清重启条件与所需预算） |

**第二问：代码写在哪？**"写在哪，决定这行代码是资产还是负债。"
- **负债区**（写死在客户环境的产品副本）：短期最快，长期最贵——只活在这一家客户、只有你能维护、产品每次升级都要人肉对齐，谁写谁背一辈子锅。
- **隔离区**（feature flag / 配置层）：特殊逻辑进统一代码库，开关只对这家客户打开；产品升级跟版本走；将来别的客户也要，把开关变成正式功能即可。
- **资产区**（平台层）：把 gap 抽象成通用能力，这家客户是第一个用户但不是唯一用户，每一行都是给下个项目省的时间。

纪律两句话："**别把特殊逻辑写死在负债区，也别把伪装成通用需求的特殊逻辑硬塞进资产区。**"AI 时代的提醒：客户提特殊需求 AI 一小时就能写完，负债区的诱惑更大——"写在负债区的代码，AI 帮你写得再快，它也还是负债，只是你欠债的速度变快了。"

**第三问：集成和迁移怎么做？**（新客户上线的沉默杀手是集成，不是模型效果）
1. **把连线变成清单**：架构图上每根外部连线落地成明细——对接哪个接口、什么方式鉴权、数据字典谁说了算、限流多少、有没有测试环境、联调窗口找谁约，评审逐项确认。
2. **先打通一条最细的真实链路**：开工第一周在客户真实环境打通一条端到端数据链路，哪怕一天只同步一条记录——目的是把鉴权、网络、权限这些看不见的承重墙提前"撞"出来。
3. **数据迁移先彩排、先定对账标准**：别上来跑全量；试跑前就与客户约定"对上账"的定义——对哪几个指标、允许多大误差、谁签字确认。不定对账标准，账就永远对不完。

补充：给集成单列预算、预留长尾场景资源；私有化尽量在商务阶段拦（"能在商务阶段拦住的私有化，是最便宜的私有化"）；客户私有部署的模型版本老时，**施工前先拿评估集在客户的模型上验证**，达不到标准的场景不做。

### 4.3 评估驱动开发：AI 项目怎么定义"好"、怎么验收

核心：客户说"感觉不太准"与你说"内部测试没问题"，是两把尺子的冲突。解法是**先定义"好"，再写第一条 Prompt**。

**四步顺序**：①与客户一起写下什么算对、什么算错、什么话绝对不能说 → ②把标准变成一条条可跑的用例（评估集）→ ③搭 harness（**Agent = Model + Harness**；模型不是自研的，Harness 才是工程团队真正的价值）→ ④才开始写 Prompt、搭 Agent。评估集随开发一起迭代，不是开工时冻结的文档。

**三类评估集**：

| 类型 | 收什么 | 上线标准 |
|---|---|---|
| **黄金集** | 核心场景标准问答；判据是"对错能否不靠人的主观判断定下来"（唯一答案可逐字校验的、规则明确可程序判定的） | **接近满分才允许上线**。坑：用例禁用"上个月""最近一周"等漂移说法；不跑在不停变化的数据集上 |
| **异常场景集** | "奇怪的星期二"：月底口径变了怎么答、账号被封数据断了怎么答、回传延迟半天口径对不上怎么答。技巧：新旧环境并行跑，**结论分叉的地方就是要找的脆弱场景** | 可逐步提升，但本次分数不得低于上一版本 |
| **安全对抗集** | 故意设套：诱导导出别的部门名单、查询提问者无权查看的数据。检验的不是会不会回答，而是**知不知道什么时候不能回答** | **一条不过，就停止上线、排查原因** |

三类分数不得合并算平均分。

**纪律**：
- "**补用例可以随时补，改用例的期望值必须慎重**"——跑不过就改低期望是 AI 项目里最容易发生、最难被发现的腐化；改期望必须有明确理由且让客户知道（这是在重新定义"好"）。"考不过就改考卷，就是自己骗自己。"
- **棘轮原则**：评估分数每上一个台阶就成为新地板，任何改动不许打穿；每次改动跑全量评估、有人对分数负责，"这次先上了再说"永远不批。
- **生产反馈回流三类**：答错/被投诉的；用户无反馈但被人工修改过的；系统判定低置信度的。筛选后补进评估集。"**棘轮防的是退步，回流带来的是进步。**"产品要预留反馈通道（同意/拒绝/争论都要能记录）——很多 Agent 把"用户没采纳建议"这个信号直接丢掉，之后想捞也捞不回来。回流涉及的数据安全要在上线前写进方案，别运行三个月后才找客户安全部门调日志。
- **分工**（项目早期商定）：评估面（系统质量、评估集维护、回归纪律）归 FDE；客户面（业务口径对不对、结果有没有价值、验收过不过）归客户。评估集由 FDE 构建维护，但**每条用例的期望值写得对不对，客户说了算**。两种失败：把评估外包给客户（没时间没方法，半途而废）；FDE 越界替客户定业务口径（验收时每个数字都可能被重新质疑）。
- **与客户共建的入口就是每周 demo**："demo 收反馈，评估集存反馈，这其实就是一条现成的流水线。"客户不会给你评估用例，只会描述自己怎么干活——用例要从描述里抽象出来。客户亲手参与定义"好"，验收就不会翻脸不认。

**验收形态**：AI 项目没有"某一天的签字"，交付的是一条还在往上爬的曲线。**按曲线谈验收**——客户才会关注坡度和迭代能力。标杆：摩根士丹利项目技术开发只用 6–8 周，打磨评估花了约 4 个月，最终理财顾问采用率 98%、研报使用量提升约三倍——那 4 个月不是验收工序，就是开发本身。

**回到现场看行为**：新版做完回客户现场坐旁边看他用——被绕着走的功能分三种处理：系统能力不够 → 补评估继续改；"好"定义错了 → 直接砍掉；设计了客户不熟悉的新流程 → 顺着原有习惯改回来。"评估集通过，只能证明系统达到了评估集定义的'好'；客户的真实使用行为，才能证明这个'好'是不是真的好。"

### 4.4 用 AI 放大交付 + 数据安全红线

**第一条线：FDE 自己用 AI 提效。** 适用环节：进场前学业务、调研取证、搭 demo、写生产代码、整理纪要、起草文档、联调对账。判断标准："**验收 AI 产出的成本明显低于自己从头完成的成本，这个选择才划算。**"代码跑一遍测试就知道对错的，放心交给 AI；要发客户的方案需逐字看完。（Glean 调研：数字工作者平均每周花 6.4 小时给 AI 补上下文、检查输出、纠正错误——botsitting 是真实成本。）

**第二条线：把 AI 做进产品（规模化"陪跑"）。** To B 老问题："功能很强大，但我们用不起来"——缺的是把功能转化成方案的人。做法：把现场判断变成 Agent 的知识、流程和规则。衡量 Agent 好坏四个指标：成功率、平均响应时间、**用户转化率**（原来只能找 BI 的人现在多大比例自己解决）、满意度。Agent 化改变交付三个核心指标：席位渗透率（10 人 → 100 人）、实施培训成本、支持工单量。

**知识库四层（不要混在一起）**：①产品使用知识（最标准）；②跨行业共性知识（RFM、生命周期等通用方法论）；③行业特有知识（电商 GMV 口径、金融合规）；④**企业特有知识**（这家客户的指标定义、术语、组织架构——最难获取但属于客户，一个字不能带出门）。三个坑及解法：长尾场景占八成精力 → 拆成结构化"场景到解法"映射；上下文缺失（"上周的数据怎么样"）→ 维护用户画像+澄清选项；口径差异（销售和财务的 GMV 不同）→ 多口径管理、按提问者部门回答。经验数字：同一 Agent、同一套 Harness，换不同一线模型性能差不多（内部场景约 99%，客户环境约 90%，差距在知识库与口径成熟度）——"**模型已经足够聪明了，真正的天花板是你的知识结构。**"

**工程原则："AI 加规则，双重兜底"**：确定性的事情交给规则，模糊的事情交给模型。

**安全护栏五项检查表（AI 功能上线前逐项过）**：
1. **字段级权限控制**：Agent 的数据访问继承提问者本人的权限——**提问者看不到的数据，Agent 也不能替他看到**；
2. **明细数据脱敏设置**：汇总可以答，明细是否脱敏；
3. **操作白名单与最小权限**：只给完成任务所需的最小权限；
4. **审计机制**：每一次回答和操作都留痕，出问题能查到在哪一步；
5. **回执确认与可回滚**：执行前清晰展示动作请用户确认；不可回滚的操作先改造（快照/版本/软删除/补偿），改造不了的移出自动执行白名单，只允许 Agent 出方案、由人执行。

配套原则：**权限跟着自主权走——自主权升一级，护栏就要加一层**；合规要求做进配置（按客户开开关），不靠交付人员"记得处理"；Agent 不确定时主动澄清，高风险交给人授权。

### 4.5 上生产 SOP：让 CIO 放心

核心认知：**"个人好用和企业可用，是两个完全不同的问题。""上生产不是一个时刻，而是一组需要逐项完成的检查。"**

**六项上线检查清单**：
1. **评估过线**：黄金集接近满分、异常集不低于上一版、对抗集全部通过；
2. **真实规模下的性能与成本**：demo 10 人、沙盒 100 人、生产可能 1 万人；评估集 100 条 vs 生产一天 10 万条——延迟与 token 账单要用真实规模完整验证；
3. **安全与权限**：§4.4 五项护栏逐条检查；
4. **全链路留痕与决策可追溯**：审计要备齐四类材料——决策依据（引用了哪些数据/政策/配置）、数据来源（API 拉的、客户报的、还是模型推断的）、操作记录（时间、谁触发、前后状态）、反向回滚（能否撤销、窗口多长）；日志留存期与监管时间窗口对齐；
5. **应急与回滚预案**：模型不响应怎么降级、Agent 异常怎么一键停止、数据回滚是否演练过——"**预案没演练过，约等于没有。**"
6. **运营与交接流程**：谁值班、谁接告警、客户侧谁处理一线问题、**谁负责把生产问题回收进评估集**——责任人没定，效果曲线就停在上线那天。（第五、六项最容易被省略，也最容易出问题。）

六项通过后**灰度上线**：从小流量、低风险部门和场景开始，运行一两周确认观测数据再逐步放量。上生产是持续观测、随时可回退、逐步放量的过程。

**五类治理风险表（一页纸两列名字：客户决策人 + FDE 对口人）**：

| 风险 | 客户侧决策人 | FDE 提供的判断依据 |
|---|---|---|
| 模型风险（答错的业务后果） | 首席风险官 / 数据科学负责人 | 评估数据 |
| 数据风险（泄露、漂移、投毒） | 安全负责人 | 权限与脱敏配置证据 |
| 工作流风险（被 AI 重设计的流程出错） | 运营负责人 | 全链路操作记录 |
| 供应商风险（断供、涨价、SLA） | 采购 | 尽调、条款、备选与切换演练 |
| 治理风险（留痕不完整、无法应对合规问题） | 合规团队 | 留痕与审计材料 |

另需约定事故定性人。"**风险没有明确到具体的人，就等于没有管。**"边界把握：不大包大揽（"出了事我们全兜着"），也不甩得干干净净——该承担的写进合同和 SLA，不该承担的会上讲明白。

**人工检查点（HITL）分级**：自动执行 / 执行后通知 / 执行前确认——大多数动作放前两级，人聚焦第三级。设少了错误累积，设多了审批疲劳等于没有检查。**授权升级看两个指标：建议采纳率、采纳后效果的兑现率**，且要在更长时间窗口、更多用户和账户上稳定后再放权——"**放权的节奏应该由数据决定，而不是由意愿决定，哪怕这个意愿来自客户自己。**"（课程案例：某天投手直接采纳了 80% 建议，团队没有顺势上线"一键采纳"——一天的盘面不是常态，兑现率数据还没回流。）边界也要能往回收：满意度、投诉率持续恶化，就缩小 Agent 自主范围。

**强监管行业加三条检查**：①模型、数据、代码和最终决策权分别由谁掌握——合同和方案阶段说清，越晚确认返工越贵；②评估集和 Harness 能否在客户指定的模型与环境里运行——不能只在供应商最熟的模型上测过就把适配留到部署阶段；换模型/升级都要重做回归评估，保留版本记录与回滚方案；③客户要求源代码交付或本地编译时——源代码交付、知识产权归属、代码使用权是三件不同的事，写进合同；发布流程要支持可复现的本地编译，做好依赖核对、密钥与客户数据清理。

> "工业时代的信任靠合同，互联网时代的信任靠口碑，**AI 时代的信任，是被审计出来的**。"花在"可审计"上的工程时间，很可能不比花在决策算法上的时间少——这笔投入要提前写进预算。

### 4.6 项目中的客户洞察

- 客户在 demo 上点头 ≠ 验收；客户说话可能客气，但**行为不会说谎**——被绕着走、用一半切回 Excel 的功能就是最诚实的反馈。
- 客户只敢把"能确认没有遗漏"的工序交给 Agent——所以**贴着客户原有工作流设计**："客户怎么工作，产品就怎么组织。"课程反例：放弃"诊断卡片流"新概念，改按 Meta 广告后台原有结构组织诊断结果——客户在新概念里无法核对完整性，会回后台重查所有广告，对诊断将信将疑。
- 客户把最核心的业务数据交给你，是信任的顶点：**效果不好可以改，数据泄露了无法撤回**——一次事故可以清零信任且再也无法恢复。
- 面对非技术决策者，谁替你"翻译"技术方案不受你控制——翻译错了，代价算在你的项目头上。

## 5. 阶段四（项目后）：交接、沉淀与复盘

### 5.1 交接：自治三级阶梯

FDE 主导运行、客户跟着学 → 客户负责日常运营与一线问题、FDE 退到后方支持 → 客户独立运行、处理常见故障、持续改进，FDE 只处理平台层问题。
**毕业标准不只看系统上线**：值班、告警、知识维护、评估集责任，是否真正转移给了客户。课程标杆：Palantir×坦帕综合医院第四阶段，新应用改由医院内部团队和医师科学家自己设计部署——**FDE 真正的交付物还包括一个有能力的客户团队**。"系统会过时，一个被 FDE 带出来、会用数据说话的客户团队，才是复购和口碑的来源。"

### 5.2 结项沉淀清单（不完成，不算正式结项）

一页纸写三件事：①这个项目学到了什么；②哪些经验已形成**平台提交**（四要素：现象—什么场景遇到问题 / 根因—本质缺什么能力 / 建议—能力抽象出来该是什么形态 / 受益面—还有哪些客户会用到）；③哪些内容明确不值得沉淀、为什么。

**单客户成果 → 产品的节奏**（按月/季度滚动做产品化决策）：把周期内积累的定制分三类——①已出现重复需求的（pipeline 里至少还有一个客户提过类似需求）→ 优先通用化；②只适用于单一客户的 → 保持原样，不强行抽象；③介于两者之间 → 先做成模板。**锚点始终只有一个："有没有第二个客户会走这条路。"**

**沉淀三层次**：沉淀代码（功能做成通用开关）→ 沉淀模式（一类客户的共性做成模板）→ 沉淀抽象（整个行业的业务抽象成可复用语义模型，即 Palantir 的 Ontology——等第二个样本出现再做，抽象的单位是业务语义，不是代码）。

**沉淀仪表盘（三指标 + 一危险信号）**：第二客户时间（第二次比第一次快多少）；单位经济（第二次成本是不是第一次的零头——加人买得来速度，买不来毛利）；平台提交率（多少条现场学习变成了路线图功能）。危险信号：**客户专属代码比通用代码增长得还快 → 正在滑向咨询陷阱。**

**私有知识转化 SOP（AI 时代 To B 的护城河）**：
- **边界三问**（决定一条知识归你还是归客户）：拿给同行业下一家客户看，原客户会觉得被泄密吗？里面有能回溯到具体企业的数字、名称、组织细节吗？它描述的是行业怎么运行，还是这家企业怎么运行？——三问全过才进可共享的行业层，有一条过不了就留在客户层。"私有知识的'私有'，是相对同行而言，不是相对客户而言。"
- **四步转化**：**抽取**（项目沉淀清单+复盘+结构化访谈；最高效的通道是产品交互记录——用户对 Agent 建议的同意/拒绝/争论，"客户的不信任，恰恰是 Agent 最昂贵的训练数据"；关键是及时，aha moment 过三个月就想不起来）→ **脱敏**（只抹客户名字、数字细节原样保留 = 没脱敏，懂行的人一眼猜出是哪家）→ **结构化**（三种形态：Context 背景性知识 / Skill 操作性知识 / Workflow 流程性知识——"文档驱动，AI 放大"）→ **入库**（版本管理、评估集覆盖、持续迭代；知识库没人负责更新，上线那天就是质量巅峰）。
- 个人习惯：每个项目结束写下**三条脱敏后的行业规律**，积累两年，这个知识库就是你和别人最大的差别。
- 护城河再定义："存量代码是包袱，需求理解、行业 know-how、客户信任，这三样才是资产。""产品只是能力在某个阶段的载体，能力本身才是护城河。"警惕把"客户离不开"当护城河——被绑定而离不开，和因持续创造价值而选择，是两回事；永久拐杖是反模式。

### 5.3 五步复盘框架

1. **目标**：当初立项确定的目标是什么？用业务语言还是技术语言描述的？
2. **实际结果**：最终拿到什么结果，数字是多少，与目标差多少？
3. **差距归因**：场景选错？施工失误？还是 AI 能力不足导致用户不愿用？（归因到**环节**，不归因到个人；主持人控制此步时长，别开成甩锅会）
4. **可复用资产**：项目给公司留下了什么——管理改进点、行业知识、平台能力、抽象出的模式、还是被带出来的新 FDE？（**分水岭在此**：目标全部达成但零资产，按课程标准只算勉强及格，不算跑通。逐条列出并写明归属人。）
5. **下一步**：基于这些资产，接下来打哪一仗？

**复盘会三要点**：①项目经理、一线 FDE 之外**让销售参与**——当初说好的目标经常只有销售记得最完整，销售也离客户最近；②产出物就是**一页纪要**，五步各占一段，一页写不下通常说明还没复盘清楚；③既不能开成庆功会，也不能开成批斗会。

> **跑通的标准：业务结果、可复用资产、下一步，三者同时成立。**

### 5.4 止损与退出

**项目级止损三条件（同时满足即启动退出评估）**：
1. 项目失去核心赞助人，三个月内找不到新的支持者；
2. 真实使用量持续下降，却找不到原因；
3. 项目中可复用的资产已经基本提炼出来。（意味着：有些项目商业上失败，资产上可以是赚的——沉淀清单写完、平台提交做完，跟客户体面分手，这一单就没白做。）

退出评估**不要让项目负责人自己主持**（沉没成本会绑架决定），换一个交付线之外的人牵头，结论会诚实得多。"进场前谈好的退出条件，还得有人在翻车的时候真的敢启用。"

## 6. 风险专题：六大失败模式与中国六大坑

### 6.1 六大失败模式（症状 → 解法）

| 失败模式 | 症状 | 解法 / 预防 |
|---|---|---|
| **咨询陷阱** | 客户专属代码比通用代码长得快；做的是"借软件开展的高端咨询" | 像遵守交付期一样遵守平台提交纪律；拒绝沉淀不回平台的交付 |
| **每客户雪花化** | 新客户进来第一反应是"这家不一样，要单独做"（连续出现即开始雪花化） | 每次部署必须留下一套可复用的模式，否则不算真正完成 |
| **英雄工程师** | "这个客户只有老王能处理"——听着是表扬，实为严重风险信号；他一走输出严重受影响 | 每个客户至少两名工程师；关键认知写成文档；把"只有一个人懂"当风险来管理 |
| **demo 债务螺旋** | demo 允诺的体验生产撑不住，团队反复填补差距而非推进交付 | 不靠过度承诺就拿不下的单子，一开始就果断放弃；主动暴露脏数据；不压缩硬化阶段 |
| **赞助人崩塌** | 力挺的高管离职/调岗/失势，新领导引入自己熟悉的供应商 | 至少两个赞助人；尽快建立自下而上的真实使用；救不回来就止损 |
| **倦怠死亡螺旋** | 从最资深的人率先离开开始：资深走→压力传导→离职加速 | 刻意轮换（同一客户连续两个季度没有新学习产出即轮换）、强制休整、同伴互助、清晰的成长通道 |

**跨模式预警仪表盘（每季度看组合，不看单一）**：客户专属代码持续增加；新客户部署周期持续缩短（反直觉项：与其它信号同现时，"快"可能只是复制定制或省略了工程化补强）；资深工程师流失率上升；可支持项目的高管储备越来越少。

### 6.2 中国六大结构性风险（体检问题）

1. **利润坎**：客单价和利润率，养得起现在这支 FDE 团队吗？
2. **人才坎**：过去半年有没有想留的工程师因"不想驻场"离开？真问题是驻场本身，还是驻场没带来成长？
3. **晋升坎**：有没有一条不离开专业一线也能成长的路径？
4. **抽象坎**：回看最近三个项目，沉淀了什么跨客户可复用的东西？
5. **组织坎**：现场 FDE 修改一个方案要经过几级审批？授权不足会持续消耗客户信任。
6. **市场坎**：最近输掉的订单，是输给更好的方案，还是输给低价？

**体检用法**：先按六大失败模式识别症状（出了什么问题），再按六道坎追结构性原因（为什么总会出这个问题）。每项红/黄/绿评分，至少两位一线 FDE 参加（一线感受比报表更早暴露问题）；不求全绿——选分数最差的一道，下季度只针对它做一个改进动作，下次体检先复查这道。

课程警示案例：IBM Watson × MD 安德森——累计花 6200 万美元、系统从未真正用于一位患者；一手推动项目的高管离开后项目崩塌，最终以审计报告收场（审计明确说不评价技术，只审采购、超支和治理——**项目先在组织层面出问题，技术还没接受检验**）。

## 7. 客户洞察专题

### 7.1 中国 To B 客户的底层画像

- **六大特征**：关系销售、定制开发、价格低廉、拖欠尾款、私有部署、现场服务。它们大多是甲方在"风险与责任错配"下的**理性自保**，而非恶意——乙方卖的是工具，甲方要的是结果；风险几乎全压在甲方身上，甲方就用手里有的手段自保。
- **病根**："标准的软件，撞上了不标准的流程。"中国把西方几百年的管理标准化压缩到几十年，流程野蛮生长、因人而异因老板而异且随时在变。解法方向：**让软件去适配流程，而不是让流程去适配软件**——派懂业务又懂技术的人到现场，一个场景一个场景把 AI 交付进去（正是 FDE 路线）。
- 一句话画像："**甲方要的是私房菜，付的却只有沙县小吃的价。**"
- 客户的验收标准已经走到"跑出效果"；效果要拿数字说话——一开始选的场景无法衡量、无法归因，"客户觉得没效果、你觉得很委屈"的僵局在立项那天就注定了。
- 客户的隐性成本要提前说清：FDE 模式要求客户开放业务会议、给真实数据权限、配懂业务的人陪磨合——这是双向筛选，也是承诺深度的信号。
- 行业集体教训："过去十年所有的勤奋（堆人、堆驻场、堆定制），某种意义上恰恰是交付做不好的原因之一"——堆人总能扛过单个项目，就永远用堆人对付本该由产品和模式解决的问题。

### 7.2 客户组织里的人性面

- 干系人动机各不相同，方案要对每一种"在意"都有交代（见 §3.3 地图四问）。
- "**外来者说一百句，不如自己人说一句**"——灰度期培训客户内部的 champion，让推广由客户自己的人来做。
- "同样一个系统，**警报发给谁，决定了它是救命工具还是背景噪音**"（坦帕案例：不发给照顾 6 个患者、警报混在 40 个提醒里 95% 被忽略的床旁护士，发给专职响应团队）——采纳设计要落到组织与工程，而不是指望用户自觉。
- 合规与安全部门不只是把关人，还是治理能力的直接使用者——早让他们参与方案与预算评审，他们就成为内部支持者。
- 监管者自己也在用 AI（如英国 FCA 用 Foundry 做反欺诈、覆盖 4.2 万家受监管机构）——整个行业的治理水位在被抬高，治理能力会持续有买家。

### 7.3 分行业客户速查表

| 行业 | 客户真正买什么 | 推荐进场路径 | 验收口径 | 关键红线 / 注意 |
|---|---|---|---|---|
| **金融** | 控制权 + 合规可交代："业务部门买功能，合规部门买'出了事说得清'" | 两条路径：先做反洗钱等合规场景建信任再进核心业务；或直接进承保/信贷等核心业务（价值上限高）。"进场时考虑阻力，扩大时考虑价值和资源" | 调查时间缩短约一半、可调查覆盖率 30%→100%、承保周期压缩 5 倍、准确率 75%→90%+（行业公开口径） | 本地部署、国产模型、代码控制常见；要求代码的目的多是供应商变更后的可持续运维而非竞争——源码交付/知识产权/使用权三件事分开写进合同 |
| **政企** | "在自己指定的环境里，把 AI 稳定运行起来的能力"（信创基本无讨价还价空间） | 本地部署国产开源模型起步；统一部署、分级复用 | 场景价值 + 自主可控的证据 | 模型、数据、平台、运行责任必须在甲方主导体系内；换模型不可怕——评估集和 Harness 扎实即可，升级用同一套评估集做回归测试说服客户 |
| **医疗** | 风险可控前提下的效率 | 按风险分级：监管文档（AI 生成+人审核）→ 医院日常运营（自动化+人看例外）→ 临床决策（系统盯数据、人拍板、全程留痕） | 死亡率下降 68%、住院时长下降 30%、周转时间改善（坦帕口径），不是模型准确率 | 最终决策权永远在人；文档生成再快过不了审核价值为零 |
| **制造** | 损益表上的数字："良率提高 0.5 个百分点""库存周转加快一成"，而不是"帮工程师每天省两小时" | 价值三级跳：提效（排产，1 分钟重排）→ 提质（良率/缺陷/返工）→ 降本（汇总成一笔经营账）。数据基础围绕选定场景建，不必先铺大而全平台 | 良率、缺陷率、返工率、报废损失的真实改善；多用例逐个归因再汇总，防止价值算重 | "确定性归规则，概率归模型"——概率模型输出必须过确定性闸门才能碰物理世界；数据地基验收三问（指标能否追到源系统/实体能否跨系统对齐/老师傅的 Excel 进系统了吗） |
| **能源** | 非生产时间（设备每停一小时都是真金白银）+ 安全保供 | 先作业优化（钻井、检修——价值容易计算，值得优先评估）再风险识别 | 减少的非生产时间换算成设备、人力和产量损失 | "安全红线的判断权，永远在人"；行业私有知识极深，客户愿意下场共创模型底座 |
| **零售/客服** | 直接反映到收入成本的经营指标（离钱近，效果定价最容易成立） | 零售两层：用户运营（会员/复购——数据全、周期短、易归因，RaaS 分成多在这层）→ 商品运营（组合/定价/配货——价值上限更高、难度也更高）。客服三级：答得准（拦截率）→ 能动手（调业务系统、人决定）→ 敢托付（规则额度内自主执行） | 拦截率（**口径先写清**，否则效果分成无法计算）+ 满意度 + 转人工后解决率一起看；增量 GMV 分成按基线 | "**托付三级跳铁律：每上一级，护栏和审计就要加一层**"；永远保留转人工选项（Klarna 回摆的教训：情绪价值只能由真人提供）；强行拦截让人深恶痛绝 |

**行业篇总纲："行业只是变量，方法才是常量。"** 施工骨架五步：找到值得解决、又能验收的问题 → 进现场把数据、规则和专家知识连接起来 → 按行业风险划清 AI、人与系统的边界 → 上线后用真实业务指标验证 → 把共性能力沉淀回产品。案例数字只能帮判断价值量级，不能直接变成对自己项目的承诺。

## 8. 关键原则速查（35 条，按生命周期排列）

**售前与立项**
1. 先找真问题，再谈 AI——别拿着锤子找钉子。
2. 一个没有退出条件的项目，不是项目，而是一份无底洞式的支持合同。
3. 外包的客户不用改变自己，FDE 的客户必须改变自己。
4. 敢不敢写"放弃"，是检验你在做 FDE 还是在做外包的试金石。
5. 沉淀没做到位就去对赌，那不叫商业模式创新，那叫赌博。

**调研与方案**
6. 客户嘴上说的需求只能信一半——那常常是他自己想出来的解决方案。
7. 在客户现场亲眼看一遍真实工作流程，比坐在办公室听一百场汇报都管用。
8. 人对着空气说不出真需求；对着一个具体的东西，意见就会冒出来。
9. 问"上周二下午三点你在忙什么"，别问"你们一般怎么做"。
10. 系统不是坐在办公室设计出来的，是从一个场景一个场景中长出来的。
11. 你只有一次用最小成本撬动最大信任的机会。

**人与信任**
12. 你的技术价值，必须先通过"人"这一关，才能落到业务上。
13. 在客户现场，汇报本身就是交付的一部分。
14. 只有单一赞助人的项目，签单的时候有多顺，崩塌的时候就有多快。
15. 客户信任你，恰恰是因为你有立场、有判断，会对他说不。

**demo 与施工**
16. demo 的第一作用不是让客户说"哇塞"，而是让客户说"不对"。
17. 宁可窄，不能断。
18. demo 赢来的不是合同，而是继续往下走的资格。
19. 写在哪，决定这行代码是资产还是负债。
20. 新客户上线的沉默杀手不是模型效果，而是集成。
21. 能在商务阶段拦住的私有化，是最便宜的私有化。

**评估与上生产**
22. 先定义"好"，再写第一条 Prompt。
23. 考不过就改考卷，就是自己骗自己。
24. 棘轮防的是退步，回流带来的是进步。
25. 提问者看不到的数据，Agent 也不能替他看到。
26. 预案没演练过，约等于没有。
27. 风险没有明确到具体的人，就等于没有管。
28. 放权的节奏由数据决定，而不是由意愿决定——哪怕这个意愿来自客户自己。
29. 个人好用和企业可用，是两个完全不同的问题。

**沉淀与复盘**
30. 有没有第二个客户会走这条路。
31. 内环让客户满意，外环让公司值钱。
32. 服务陷阱不是做了定制，而是定制无法毕业。
33. 业务结果、可复用资产、下一步三者同时成立，项目才算跑通。
34. 客户的不信任，恰恰是 Agent 最昂贵的训练数据。
35. AI 时代的信任，是被审计出来的。
